# Рендер клипа на Colab GPU

`scripts/colab_render.sh` принимает те же аргументы, что `node render.mjs --clip=…`, и раскидывает кадры по нескольким Colab VM.
Результат ложится в тот же `--out` и по формату совпадает с локальным рендером: h264 High, yuvj420p (pc), crf 19 medium, 24 fps, AAC 192k.

```bash
scripts/colab_render.sh --song=tokensENr --clip=0:264.811 --out=out/reels/btt_full.mp4                 # 2xL4 + 2xA100: ~17 мин, ~4 CU
VMS="L4 L4" scripts/colab_render.sh --song=tokensENr --clip=0:264.811 --out=out/reels/btt_full.mp4     # ~32 мин, ~1.7 CU
```

Переменные окружения:
- `VMS` — типы VM, по умолчанию `"L4 L4 A100 A100"`. Colab даёт максимум 2 сессии одного типа.
- `JOBS` — число Chrome на VM, по умолчанию 6 (12 даёт столько же).
- `MAXMIN` — жёсткий лимит в минутах, по умолчанию 45.
- `CHUNK_MIN` — минимальный кусок в кадрах, по умолчанию 36.
- `CHROME_VERSION`, `CHROME_GL`.

Если Colab отвечает 503 / TooManyAssignments / «Allocation refused» (например, все L4 заняты рендером clipforge), рендерить локально через `node render.mjs`.
После любого запуска `colab sessions` не должен показывать `bt-*`. Скрипт проверяет это сам и выходит с кодом 1, если что-то осталось.

## Замеры (2026-09-30, `--clip=40:50`, 240 кадров, одна L4)

| | мс на кадр | кадров/с |
|---|---|---|
| Mac mini, 1 Chrome | 395–580 | 1.7–2.5 |
| L4 VM, 1 Chrome | 1280 | 0.78 |
| L4 VM, 6 Chrome | 3200 на каждый Chrome | **1.68** |
| L4 VM, 12 Chrome | | 1.69 |

- Одна VM примерно равна маку.
- Время от запуска до mp4: 175 с. Из них `new` 4 с, `ready` 30 с, рендер 143 с, потом ~1 с на сборку.
- Узкое место — CPU VM: 12 vCPU, то есть 6 ядер Xeon 2.2 GHz. Кадр — это p5 WEBGL + p5.brush в JS (`redraw` 1.2–1.5 с против 0.6–0.7 с на маке) плюс `toDataURL` JPEG 0.1–0.3 с.
- GPU загружен на 27%, поэтому A100 не быстрее L4, а стоит в 3.4 раза дороже.

Полный клип v2 (264.8 с, 6355 кадров). Оценка по логу полного рендера 2026-10-01 при равных диапазонах: VM закончили за 680 / 950 / 900 / 1200 с, всего ~0.59 с на кадр на VM.
- `L4 L4 A100 A100` с очередью → ~16 мин рендера + ~1 мин на старты Chrome в кусках + ~0.5 мин подготовки ≈ **17 мин** (было ~20 из-за перекоса). Цена ~4 CU (L4 1.54 CU/ч, A100 5.30 CU/ч).
- `L4 L4` → ~32 мин, ~1.7 CU.
- Мак: ~42 мин при 395 мс/кадр.

Тест очереди 2026-10-01: `VMS="L4 L4"`, `--clip=40:60`, 480 кадров.
- 14 кусков по 36 кадров, VM взяли 8 и 6 кусков.
- 187 с от запуска до mp4, 480/480 кадров, формат как у локального.
- Кадры 0, 35, 36 (стык кусков), 250 и 479 против локального рендера: SSIM 0.94–0.96. Соседний кадр даёт 0.92, так что стык не сдвинут.

## Сверка с маком

Кадры 40, 120 и 200 с Colab против свежего локального рендера: SSIM 0.95–0.96, визуально совпадают.
Разница только в сглаживании текста (Linux против macOS) и шуме кодека.

Страница stateless: `randomSeed` / `noiseSeed` выставляются на каждый кадр, мемоизации (`FREEZE`, `HITPX`) детерминированы. Поэтому кускам не нужен pre-roll: кадр 120, отрендеренный с начала куска, совпадает с кадром из сплошного рендера.

Единственное, что было не так, — **шрифты**. `setup()` грузил Russo One только под пробный текст `'КРЕМЛЬ'`, поэтому латинский сабсет подгружался лениво, и первые кадры любого запуска рисовали заголовок и сабы fallback-шрифтом.
Теперь `render.mjs` после `window.ready` загружает все `@font-face`. Это касается и локального рендера: его первый кадр тоже был с неправильным шрифтом.

## Устройство

1. **Бандл** (~0.7 МБ): `render.mjs`, `package*.json`, `*.html`, `src/`. Аудио не едет на VM, `node_modules` ставится через `npm ci`.
2. **VM** (параллельно):
   - `colab new` с 4 попытками;
   - ssh с ControlMaster (Colab пускает одно ssh на runtime);
   - `vm_setup.sh`: json вендора EGL для NVIDIA, Chrome for Testing той же версии, что на маке, недостающие .so, `npm ci`, статический ffmpeg 8.1 (BtbN);
   - проверка `UNMASKED_RENDERER = NVIDIA`.
3. **Очередь кусков (work stealing).** Клип режется на куски, которые к концу уменьшаются: размер = `max(CHUNK_MIN, ⌈остаток / (2 · VM · JOBS)⌉)`. Для полного клипа на 4x6 это ~133 кадра в начале и 36 в хвосте, всего ~110 кусков.
   - У каждой VM `JOBS` слотов. Слот на маке забирает следующий свободный кусок (`mkdir` в `$TMP/q` — атомарный замок) и запускает на VM `chunk.sh c i0 i1` → `node render.mjs … --part=i0:i1`.
   - Тяжёлые сцены больше не достаются одной VM. Раньше при равных диапазонах кадров VM0 закончила за 650 с, а VM2 за 1200 с.
   - VM, которая не поднялась (503), просто не берёт куски. Упавший кусок освобождается для других слотов, а слот выходит.
   - Если в конце какого-то куска нет, скрипт падает с кодом 1.
   - `--part` рендерит только кадры `[i0, i1)` клипа, причём с тем же `t = a + i/fps`, что и сплошной рендер, так что граница буста на 12 fps совпадает.
   - Кадры идут без звука, с теми же параметрами x264.
4. **Стриминг.** MPEG-TS валиден, пока растёт, поэтому `chunk.sh` отдаёт кусок в stdout того же ssh через `tail -f --pid` прямо во время рендера.
   - Обычный scp после рендера шёл через прокси colab на ~0.25 МБ/с.
5. **Сборка на маке**: concat `-c:v copy` с явными `duration` + песня `-ss a -t (b−a)` (с `--fade` те же фейды, что в render.mjs), aac 192k, faststart.
6. **VM останавливаются всегда**: каждая, как только её слоты не находят свободных кусков, плюс `trap` на EXIT/INT/TERM, watchdog `MAXMIN` и финальная проверка `colab sessions`.

## Грабли

- ffmpeg из образа Colab (4.x) переводит полнодиапазонные JPEG-кадры в tv-range yuv420p, а ffmpeg 8 на маке оставляет yuvj420p (pc). Поэтому на VM ставится ffmpeg 8.1.
- `render.mjs` на Linux раньше ставил `--use-angle=d3d11`. Теперь флаги GL берутся из `CHROME_GL` (`--no-sandbox --enable-gpu --use-gl=angle --use-angle=gl-egl`), а путь к Chrome — из `CHROME`. Без них WebGL уходит в SwiftShader.
- Шрифты Google Fonts и `node_modules` VM качает из интернета.
- Рендерится текущее рабочее дерево, включая незакоммиченные правки сцен, как и при локальном рендере.
